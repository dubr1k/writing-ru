# writing-ru

**12 навыков для русских текстов: от первого черновика до редакторской проверки.**

Агент написал письмо — оно вежливое, но просьба спрятана в третьем абзаце. Подготовил статью — источники есть, а вывод повторяет введение. `writing-ru` задаёт порядок работы с такими задачами: сначала читатель и факты, затем мысль и жанр, после — редактура.

Набор рассчитан на [Hermes Agent](https://hermes-agent.nousresearch.com/docs/). Это Markdown-инструкции и небольшой Python-скрипт, а не отдельная модель или сервис. Скрипт работает локально, без API, зависимостей и отправки текста в сеть. При работе через агента материалы могут передаваться его модельному провайдеру — это зависит от вашей настройки Hermes.

## Как работать

```text
Читатель и задача → факты и источники → главная мысль
                 → ядро + жанр → черновик → скрипт + ручная редактура
```

Текущее задание важнее стилевых предпочтений навыка. Если журнал требует пассивных конструкций, а письмо — формальной формулы, не нужно ломать их ради нулевого отчёта. Правила безопасности и разрешения на запись или отправку также сохраняются: навык подготовки письма не разрешает отправлять его.

После установки можно явно вызвать навыки в чате Hermes:

```text
/russian-text-craft /ru-business-correspondence
Сократи письмо до 150 слов. Просьбу поставь первой. Не меняй сроки и условия.
[исходное письмо]
```

```text
/russian-text-craft /ru-analytical-note
Сравни два предложения по приложенным материалам. Сначала дай вывод,
затем основания и неизвестное. Не додумывай цены и характеристики.
```

Для авторского текста приложите разрешённые образцы и свою позицию. Если их нет, агент должен уточнить недостающее или предложить нейтральный вариант, а не сочинять личный опыт.

## Установка в Hermes

Нужны установленный Hermes, Git и Python 3.10+ для скрипта. Сам набор не устанавливает и не обновляет Hermes. Если Hermes ещё нет, начните с [официальной установки](https://hermes-agent.nousresearch.com/docs/getting-started/installation) и [quickstart](https://hermes-agent.nousresearch.com/docs/getting-started/quickstart).

Ниже — команды для Bash на Linux, macOS или WSL. Используется ручная установка файлов; она не проходит проверку Skills Hub. Перед копированием прочитайте навыки и скрипт. Инструкция сверена с документацией [Skills System](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills) и [Profiles](https://hermes-agent.nousresearch.com/docs/user-guide/profiles).

### 1. Получите отдельную копию

В свободной рабочей папке:

```bash
git clone https://github.com/dubr1k/writing-ru.git
cd writing-ru
python3 -I -m unittest discover -s tests -v
```

### 2. Явно выберите профиль

Навыки лежат в `skills/` выбранного Hermes home. У именованных профилей свои каталоги. Не копируйте набор сразу во все профили и не меняйте глобальные настройки.

```bash
# По умолчанию — HERMES_HOME, если задан, иначе стандартный home.
TARGET_HOME="${HERMES_HOME:-$HOME/.hermes}"
# Для другого профиля вместо строки выше укажите его реальный home:
# TARGET_HOME="$HOME/.hermes/profiles/writer"
printf 'Установка в: %s\n' "$TARGET_HOME"
```

Проверьте напечатанный путь. Переменная `TARGET_HOME` выбирает место установки, но сама по себе не переключает запущенный Hermes. Открывайте тот же профиль, в который установили набор. Не выбирайте каталог, который уже является общей ссылкой на чужое хранилище навыков, без согласования с его владельцем.

### 3. Скопируйте семейство без перезаписи

Из корня checkout, в том же Bash:

```bash
(
  set -eu
  : "${TARGET_HOME:?Сначала выберите Hermes home}"
  target="$TARGET_HOME/skills/writing-ru"
  if [ -e "$target" ] || [ -L "$target" ]; then
    printf 'Остановка: %s уже существует; ничего не перезаписано.\n' "$target" >&2
    exit 1
  fi
  mkdir -p "$TARGET_HOME/skills"
  cp -R skills/writing-ru "$target"
  test -f "$target/russian-text-craft/SKILL.md"
)
```

Откройте новую сессию нужного профиля и попросите показать `russian-text-craft` и выбранный жанр. Если одноимённый навык уже находится в другом каталоге, разберите конфликт до использования; наличие файлов ещё не доказывает, что агент выбрал именно эту версию.

Копия изолирует правки профиля от checkout. Символьная ссылка тоже возможна, но связывает их: агент, редактирующий установленный навык, сможет изменить репозиторий. Поэтому копирование — рекомендуемый вариант.

### Обновление и удаление

Сначала сохраните собственные правки. В чистом checkout выполните `git pull --ff-only`, просмотрите изменения и снова запустите тесты. Для установленной копии безопаснее переименовать **только ваш** каталог `writing-ru` в резервный каталог вне `skills/`, затем повторить шаг 3. Сравните старую и новую версии и перенесите свои правки вручную. Резервные копии внутри `skills/` могут создать дубликаты имён.

Для удаления сначала проверьте `TARGET_HOME` и принадлежность каталога, затем переместите только установленный вами `skills/writing-ru` за пределы `skills/`. Не удаляйте весь `skills/` или home профиля. Если ставили ссылку, удаляйте только её, а не каталог назначения. В новой сессии проверьте, что навыки больше не доступны из этого места; при дубликатах они могут оставаться доступными из другого источника.

## Проверка текста

Из корня репозитория:

```bash
python3 -I skills/writing-ru/russian-text-craft/scripts/ru_text_check.py examples/B.md
python3 -I skills/writing-ru/russian-text-craft/scripts/ru_text_check.py examples/B.md --json
python3 -I skills/writing-ru/russian-text-craft/scripts/ru_text_check.py tests/fixtures/positive.txt --strict
```

Последняя команда намеренно возвращает `1`: фикстура содержит красный сигнал. Без `--strict` успешный анализ возвращает `0`, даже если есть замечания. `--strict` возвращает `1` при поле `red=true`, а не при любой найденной фразе. В частности, красный сигнал дают три совпадения из приоритетных групп; отдельная фраза может не дать его. Ошибки чтения/разбора тоже завершаются ненулевым кодом — проверяйте stderr, а при `--json` наличие корректного отчёта.

Поддерживаются UTF-8 `.txt`, `.md`, `.docx` и stdin (`-`). DOCX читается из основного XML: абзацы, текстовые фрагменты, табуляция и разрывы строк. Колонтитулы, сноски, комментарии, оформление и визуальная вёрстка не проверяются; это не валидатор Word. Подавайте доверенные файлы разумного размера: скрипт не является изолированной средой для враждебных ZIP/XML.

JSON содержит `metrics`, `findings`, `flags` и `red`. Номера строк для DOCX относятся к извлечённому тексту, не к страницам. Метрики приблизительны: суффиксы не заменяют морфологический разбор, а разбиение предложений — лингвистический анализ. Markdown проверяется вместе с разметкой и кодом; цитаты и примеры не исключаются.

### Ложные срабатывания ожидаемы

- «Данные лежат в файле» попадает в группу канцелярита из-за широкого шаблона слова «данный». Здесь **данные** — существительное, исправлять его не нужно.
- «Вызовы инструментов» попадают в группу абстрактной лексики из-за слова **вызовы**. В техническом описании это точный термин.
- Списки, термины и повторяющийся синтаксис могут быть уместны в инструкции или методике.

Эти случаи закреплены в тестах. Не переписывайте точный текст ради зелёного статуса.

## Примеры А/Б и пределы метода

В [A](examples/A.md) — обычный ответ об акторно-сетевой теории и агентных харнессах; в [B](examples/B.md) — ответ с явной редактурой по навыкам. [Пояснение к сравнению](examples/README.md) показывает, что изменилось и чего сравнение не доказывает.

Это один иллюстративный опыт, не контролируемый эксперимент. Baseline мог наследовать профильные инструкции; различие умеренное. Нет оснований обещать одинаковое улучшение для другой модели, темы или автора.

Набор не гарантирует качество, достоверность, авторство, отсутствие клише или обход детекторов. Статические фразы не определяют ИИ-генерацию. Нулевой отчёт не означает хороший текст; красный сигнал не означает плохой. Факты, источники и согласие автора проверяются отдельно.

## Проверка и участие

```bash
python3 -I -m unittest discover -s tests -v
```

Тесты покрывают txt/md/docx, Unicode, JSON, strict-коды, stdin, пустой текст и известные ложные находки. DOCX-фикстуры создаются в тесте и проверяют извлечение XML, а не отображение в Microsoft Word.

Предлагая правило, приложите пример, где оно полезно, и пример, где оно ошибается. Изменения порогов требуют обоснования; снижение числа находок само по себе не доказывает улучшение текста. Не присылайте личные переписки, закрытые документы и чужие образцы без разрешения.
